## 8. NOTA OPERACIONAL — o índice quase reverteu o trabalho de outra sessão

Durante esta sprint **outra sessão commitou** (`5ca27db` e `c5de6e1`, mega-menus
+ SYNC do CLAUDE.md). O `git commit` normal continua travado pelos `.lock`
órfãos de 0 byte que o mount do OneDrive não deixa apagar, então usei de novo o
contorno de `commit-tree` — **e caí numa armadilha nova**.

Para escapar do `index.lock` eu **copiei** `.git/index` para fora do OneDrive. O
índice copiado era de **antes** do `c5de6e1`. Resultado: o primeiro commit
(`50289f8`) trazia, além dos meus 5 arquivos, a **reversão** de `CLAUDE.md`
(**−31 linhas**), `app/KineoLanding.tsx` e `components/NavEngineItem.tsx` — teria
apagado o trabalho da outra sessão.

Peguei no `git show --stat` antes de qualquer push, descartei o `50289f8` e
refiz com o índice montado **na hora** a partir do `c5de6e1`. Conferência final:
os três arquivos da outra sessão têm **hash idêntico** ao do `c5de6e1` no HEAD
novo, e o diff do commit é **só os meus 5 arquivos**.

**Regra para as próximas sprints:** com os `.lock` do OneDrive, montar índice com
`git read-tree <HEAD atual>` num `GIT_INDEX_FILE` fora do OneDrive.
**NUNCA copiar `.git/index`** — ele pode ser anterior ao último commit de outra
sessão, e aí o commit vira uma reversão silenciosa.

Commit final: **`fe904eb`**, pai `c5de6e1`. `tsc` EXIT=0 no estado final.
Se o `171-PUSH.bat` reclamar de *"another git process seems to be running"*,
apague os `.lock` de 0 byte dentro de `.git` (no Windows eles saem) e rode de novo.
